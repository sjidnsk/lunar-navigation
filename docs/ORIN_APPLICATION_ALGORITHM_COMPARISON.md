# Orin 两条应用分支算法对比

对比日期：2026-09-18。算法提交基线：实车线 `69a7eae2`，Unreal 仿真线 `99aacba5`。

## 结论

两条应用分支没有形成两套规划算法。以下正式运行实现逐目录一致：

- 增量导航核心 `lunar_incremental_navigation_core`；
- 导航 ROS 节点的 `include/` 与 `src/`；
- 探索核心及探索 ROS 节点的 `include/` 与 `src/`；
- 轮式控制器的 Python 运行代码与 launch；
- `lunar_planning_msgs` 接口。

因此，全局/局部规划、5×5 地形判定、未知区域边界保留、起点补偿、探索候选与完成条件、路径跟踪和到点判定的实现相同。现场行为差异主要来自输入数据、车辆适配和参数。

## 有意保留的应用差异

| 项目 | `app/orin-real-vehicle` | `app/orin-unreal-simulation` |
| --- | --- | --- |
| 地图与位姿 | P3 地图、里程计及私有 map→odom 输入 | Unreal TCP 反馈及仿真传感器 |
| 车辆输出 | `/Car/T5/Car_Cmd_Vel` | TCP 四轮速度与转角协议 |
| 规划起点盲区补偿 | `wheel_orin.yaml` 为 3.0 m | 独立 Unreal 仿真的通用 `wheel.yaml` 未显式配置，加载默认值为 0.2 m；兼容 P3 联调模板为 2.0 m |
| 仿真传感器近场半径 | 不适用，由 P3 提供实际地图 | 2.1 m；这是虚拟观测参数，不是规划起点补偿 |
| 控制上限 | 0.2 m/s、0.1 rad/s | 独立 Unreal 仿真为 0.2 m/s、0.15 rad/s；兼容 P3 联调模板仍为 0.03 rad/s |
| 到点容差 | 0.1 m、0.05 rad | 0.1 m、0.05 rad |
| 探索观测模型 | 10 m、90° | 独立 Unreal 仿真为 30 m、360°；P3 联调模板为 10 m、90° |

`coverage_target` 只作为统计/验收参数；候选点耗尽仍是探索完成条件。不同数值不应改变完成语义。

## 非算法差异

- Unreal 分支增加 `lunar_obj_tcp_sim`、旧车辆 TCP 接口副本、协议转换、GUI 和仿真部署工具。
- 实车分支增加 P3/T5 配置、静态 TF 输入脚本和 Orin 启动脚本。
- 两边有不同的现场回归测试；测试文件差异不代表生产实现不同。
- 实车 launch 支持把相对 `platform_config` 路径解析为绝对路径；这是部署健壮性差异，不改变规划算法。

## 维护约束

通用规划、探索、地图和控制修改应先进入 `integration/pure-planner-orin`，验证后同步到两条应用线。TCP/Unreal 适配只留在仿真线，P3/T5 接口与实车能力配置只留在实车线。独立 Unreal 仿真的 0.2 m 起点补偿需按仿真地图盲区单独标定。若继续使用 TCP 分支中的 P3 联调兼容模板，应单独确认是否把 2.0 m、0.03 rad/s 调整为当前现场参数，不能把该模板当作实车配置来源。
