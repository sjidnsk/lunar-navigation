# Pure Planner 编译与节点启动指令

本文面向当前仓库：`/home/kai/CodexDownloads/lunar_navigation/lunar_pure_planner_orin`。命令分为四条互不混用的路径：

- **Humble 生产规划栈**：使用 `/Car/T3/*` 输入、`/Car/T4/*` 规划接口；可选启动轮式控制器。
- **Jazzy 月表 RViz 演示**：全部使用 `/lunar_demo/*`，不接入生产话题，也不控制车辆。
- **legacy 纯前沿探索节点**：调用已经运行的 legacy 生产规划 Action；不自动启动规划器、地图源或控制器。
- **incremental_v2 探索—导航栈**：只由局部 `GridMap`、odometry 和 `/tf` 累计建图；不读取全局先验图。

> 安全边界：`scripts/start_all.sh` 会启动 `lunar_pure_wheeled_controller`，其命令输出为 `/Car/T5/Car_Cmd_Vel`。仅在车辆控制链路获准且已具备急停/场地安全条件时使用。只做规划、RViz 或 Topic 验证时，请按“手动启动（不含控制器）”执行。

### 直接发送月表目标

月表模式需同时具备全局总览与局部图：

```bash
ros2 action send_goal --feedback /Car/T4/plan_motion \
  lunar_planning_msgs/action/PlanMotion "{
  environment_mode: 1,
  request_id: surface-001,
  mission_id: manual,
  mission_revision: 0,
  goal: {
    header: {frame_id: map},
    goal_id: surface-goal,
    goal_type: 1,

    has_yaw_constraint: true,
    yaw_rad: 0.0,
    yaw_tolerance_rad: 0.2
  },
  replace_active_request: false
}"
```

`Goal accepted` 或 Action CLI 的 `SUCCEEDED` 不能单独证明业务规划成功。读取结果时必须确认：

```bash
ros2 topic echo --once /Car/T4/planning/diagnostics
```

成功判据为 `planning_outcome: 0` 且 `has_reference: true`。无路径、输入缺失或安全约束拒绝时，系统应不发布有效参考；这是安全结果，不应以 Action 接收与否替代结果判定。

取消前台发送中的 Action：在运行 `ros2 action send_goal` 的**同一终端**按 `Ctrl+C`。替换现有请求时，发送新目标并设置 `replace_active_request: true`。

## 6.1 incremental_v2：增量地图、探索决策与导航会话

本节是独立于第 6 节 legacy 节点的新版入口。启动参数在启动前选择唯一栈，不能把两条栈并发到
同一 `/Car/T4/*` Topic，也没有自动回退：

```bash

cd "$PROJECT_ROOT"
source /opt/ros/humble/setup.bash
source "$PROJECT_ROOT/ros2_ws/install/setup.bash"

# 新版：唯一增量地图 + NavigateToPose 会话 + 薄探索决策。
ros2 launch lunar_pure_exploration_ros exploration_navigation.launch.py \
  stack_mode:=incremental_v2 platform_type:=wheel

# 明确回退：启动原有 pure planner + pure explorer，不改变其 ABI/行为。
ros2 launch lunar_pure_exploration_ros exploration_navigation.launch.py \
  stack_mode:=legacy platform_type:=wheel
```

若当前 install 尚未包含新增包，先在同一 Humble 目标环境构建依赖闭包后再 source；不要把 Jazzy
install overlay 用于 Humble/Orin：

```bash
cd "$PROJECT_ROOT/ros2_ws"
source /opt/ros/humble/setup.bash
colcon build --packages-up-to \
  lunar_incremental_navigation_ros lunar_pure_exploration_ros \
  lunar_pure_planner_ros
source install/setup.bash
```

`config/exploration_navigation.yaml` 由 `lunar_pure_exploration_ros` 安装，集中提供 `incremental_v2` 的
`stack.mode`、`platform_type`、Topic、`coarse_resolution_m`（默认 `1.0 m`）、
`navigation.local_window_size_m`（默认 `64.0 m`）和探索参数。
`config/incremental_navigation_interfaces.yaml` 记录新版接口类型与固定 QoS。显式
`stack_mode:=legacy` 不读取该 YAML，也不要求 `lunar_incremental_navigation_ros` 已安装；只使用 legacy
launch 自己的默认值及显式 `platform_type`/`use_sim_time`。不要通过 launch 参数混入全局图、current pose、
额外地图或运行时分辨率切换。

### 输入、地图和检查

incremental_v2 的环境输入只有下表；第 2 节的 `global_overview` 要求属于 legacy 月表规划，**不适用于本节**。

| Topic | 类型 | 订阅者与用途 |
| --- | --- | --- |
| `/Car/T3/mapping/grid_map` | `grid_map_msgs/msg/GridMap`（`elevation` layer） | 只由 `incremental_navigation` 订阅，增量构建唯一地图。 |
| `/Car/T3/localization/odometry` | `nav_msgs/msg/Odometry`，`odom -> base_link` | 导航器与探索器的状态输入。 |
| `/tf` | `tf2_msgs/msg/TFMessage` | 直接 `map -> odom` 变换。 |

对外位姿契约固定为 `odom -> base_link`。`config/wheel.yaml` 的
`base_frame_id: base_footprint` 仍只表示轮式 footprint 几何，不改变此 Topic/TF 契约。

第一张有效 `GridMap` 决定 fine resolution：当前 `0.2 m` 和未来 `0.1 m` 都直接按输入保持。`0.1 m`
不会重采样为 `0.2 m`；改变分辨率要重启整个 incremental_v2 栈。轮式与足式仍使用既定的可通行性和
8 邻域 A*，本接线不改变算法。`local_window_size_m=64.0` 时，局部规划窗口为 `0.2 m -> 320 × 320`
和 `0.1 m -> 640 × 640`；若按当前 fine resolution 需要超过 `640` 格/轴，周期返回
`LOCAL_WINDOW_CAPACITY_EXCEEDED`，不会静默缩小物理窗口。

导航器从同一 fine snapshot 发布正式探索图：
`/Car/T4/mapping/exploration_map`，类型 `nav_msgs/msg/OccupancyGrid`，取值固定为
`-1=UNKNOWN`、`0=FREE/CANDIDATE`、`100=PROVEN_BLOCKED`，QoS 为 Reliable + Transient Local +
KeepLast(1)。探索器只读它，不订阅原始 `GridMap`，不拥有第二个 `PersistentElevationMap`；导航器也不
订阅任务 Topic。新版探索器只接受这三个精确值，其他值发布为 `INVALID_EXPLORATION_MAP`，不会提交
goal。任务仍按第 6 节格式发布到 `/Car/T4/exploration/task`，探索器一次只维护一个
`NavigateToPose` goal。

启动后先做只读检查：

```bash
ros2 topic info -v /Car/T3/mapping/grid_map
ros2 topic info -v /Car/T4/mapping/exploration_map
ros2 action info /Car/T4/navigation/navigate_to_pose
ros2 node info /incremental_navigation
ros2 node info /incremental_exploration
```

预期第一条只有导航器订阅；第二条由导航器发布、探索器订阅；Action 为探索器 client、导航器 server。
`/Car/T3/mapping/global_overview` 与 `/Car/T3/semantic/current_pose` 不应成为本栈订阅。

### 结果判定和 RViz

规划周期成功必须在 `/Car/T4/planning/diagnostics` 中满足 `cycle_result=PLAN_FOUND`，同时
`/Car/T4/planning/path_reference` 是非空 `ACTIVE` 路径且其 segment/traversability revision 与诊断一致。
目标导航成功只以 `NavigateToPose` Action Result 的 `GOAL_REACHED` 为准；Action accepted、RViz 线条或
单独的 PathReference 都不等价于完成。

隔离 Jazzy RViz 演示使用
`lunar_incremental_navigation_ros/incremental_exploration_navigation_rviz.launch.py`，所有算法 Topic 在
`/planning_demo/*`，不会发布 `/Car/T5/Car_Cmd_Vel`。Fixed Frame 为 `map`；显示任务边界、三态任务图、
局部窗口、frontier、唯一 current goal、fine traversability、global route、active path、robot/trace 与 HUD。
必演 wheel + `0.2 m`、wheel + `0.1 m`、legged + `0.2 m` 和 `NO_PATH` 后换候选；headless
`start_rviz:=false` 只能作为闭环检查，GUI 人工视觉验收必须实际启动 RViz。

该演示标注的 `16 m` 局部观测范围是 scenario 的地图输入，不是 `local_window_size_m` 的规划窗口；
不要将 16 m demo probe 作为 64 m 窗口的容量或性能证据。

本机 Jazzy 实测命令和证据边界见
`docs/validation/2026-09-03-incremental-exploration-navigation.md`。Humble、Orin、DDS 跨机、rosbag、
真实 mapper/TF 与实车均仍为 `NOT_RUN`；不要将 Jazzy 结果外推为生产就绪。

## 7. Jazzy：本机月表 RViz 演示（测试专用）

这条路径只能使用 Jazzy，并与第 1～6 节的 Humble 生产栈隔离。它会生成 `/lunar_demo/*` 的合成 `1 km × 1 km` 全局地图（`1000 × 1000`、`1 m/cell`），并向规划器提供以车为中心的 `64 m × 64 m` 局部 GridMap（`320 × 320`、`0.2 m/cell`）、里程计和 Action，**不会**消费 `/Car/T3/*` rosbag，也不包含控制器。

```bash

cd "$PROJECT_ROOT"
source /opt/ros/jazzy/setup.bash

  --build-base build-jazzy-demo-delivery \
  --install-base install-jazzy-demo-delivery \

  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo
source install-jazzy-demo-delivery/setup.bash

# 轮式
ros2 launch lunar_pure_planner_ros lunar_surface_rviz_demo.launch.py \
  platform_type:=wheel

ros2 launch lunar_pure_planner_ros lunar_surface_rviz_demo.launch.py \
  platform_type:=legged
```

该测试 launch 显式启用 Demo 交付协议，生产默认关闭。新目标到达后，Demo 先停车并清除旧执行段。
首个目标或恢复 STOP 使用同 token 交付全局图、局部图、odometry 和 `map->odom` TF；后续 4 m 滚动周期
只重交付局部图和当前位姿 odometry。规划器只有在输入身份一致、起点处于局部窗口内，且平台输入
已就绪后才发布 ACK；同 token 重发不重建输入序列或足式投影。Demo 只执行匹配当前
`request_id + map_token + segment_index` 的 EXECUTE 信封，普通 `Path` 只供 RViz 显示。轮式与足式
均按 `12 m` 名义前视规划，每移动 `4 m` 生成新 token；ACK 前只短暂保持交付快照，ACK 后继续执行
旧段并在后台等待下一段，新段从当前位置附近的前向路径接续。仅当旧段耗尽、新目标、恢复或失败
时停车。
该隔离 Demo 的 ACK 窗口为 `10 s`，生产默认参数不变。Reporter 的 `local=` 来自已授权 EXECUTE 路径，
不再把轮式全局 preview 误报为局部执行段。

滚动模式默认允许成功段之后的局部 `NO_PATH`/`TIMEOUT` 最多恢复两次。恢复诊断包含
`rolling_recovery=true` 和 `rolling_recovery_attempt=N`，并先发布空路径使 Demo 停止旧路径；
首次失败、不可恢复错误或次数耗尽仍终止 Action。这里没有放宽输入身份检查，也没有延长每周期
`3 s` 硬截止。

在 RViz 中将 Fixed Frame 设为 `map`，初始顶视范围约为整张地图；粉紫色圆盘和 `Current rover position` 标签标记车辆当前位置。等待约 6 秒让百万格输入进入规划器，再用 **2D Goal Pose** 选择空白可达区域。预期 `/lunar_demo/path` 更新，并与轮式可通行性和采样高程同屏展示。为避开部分 Mesa/RViz 的 GLSL sampler 冲突，默认关闭原始 OccupancyGrid Display；轮式可通行性图仍显示障碍与安全判定。点击障碍物或不可达点时没有有效路径是预期的安全行为。验证命令：

## 8. 常见故障定位

| 现象                               | 先执行                                                                                                     | 处理方向                                                                    |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
