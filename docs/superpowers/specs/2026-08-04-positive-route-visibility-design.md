# 正例路线可见性修订设计

日期：2026-08-04  
状态：待用户审阅  
选择：A——只修正离线报告

## 问题与根因

当前规划证据包含三条正例路线、正例起点和正例目标，但
`platform_cases.svg` 的可见文字只解释负例。正例仅靠一条彩色折线、白色起点圆和
彩色目标圆表达，没有 `正例`、`PASS`、成功 reason code 或方向说明。因此报告在
结构上包含正例，人工查看时却容易判断为“没有正例”。

## 方案比较

1. **选定：原有三面板内增加正例标注和方向箭头。** 保持现有地图、比例和文件结构，
   改动最小，能直接解决辨识问题。
2. 将正例和负例拆成六个独立面板。最清晰，但显著扩大画布并改变既有布局和审阅习惯。
3. 在 Isaac Sim 视口绘制临时路线。适合交互演示，但会引入实时连接和视口状态，不属于
   用户选择的离线方案 A。

## 可见内容

每个平台局部面板必须同时显示：

- `正例 PASS` 和对应成功 reason code；
- 白色圆形起点、平台颜色的目标点，以及文字图例；
- 从起点到目标的正例路线和位于末段的同色方向箭头；
- 既有负例 reason code、目标容差虚线圆、叉号和“路线不适用”说明。

全局场景继续显示真实月面快照、三平台锁定起点和三条正例路线。HTML 图例补充
“白圆=正例起点、彩色圆=正例目标、叉号=负例目标”，避免依赖颜色和位置猜测语义。

## 数据与安全边界

所有正例文字和箭头仅由已验证的 v2 lock 与 `normalized_reference`/已验证跳跃弹道生成；
不得从日志、截图或手工坐标构造路线。修订不得连接 Isaac、修改或保存 USD、改变规划器、
能力文件、场景锁、快照或正式 Action 结果。HTML/SVG 仍需通过既有离线元素、属性和精确
stylesheet 白名单；不得加入脚本、网络资源或外部资产。

旧的正式可视化目录不可覆盖。修订后使用两次既有 6/6 正式运行结果，在各自新的
`visualization-positive-v1/` 目录原子发布五个文件，并要求三张 SVG 在两次运行间仍字节级
一致。

## 实现与失败处理

在外部仓的可视化生成器中增加一个只负责计算末段箭头几何的小函数；若路线没有两个不同
的有限画布点，生成必须以既有 `VISUALIZATION_RESULTS_INCOMPLETE` 失败，不能发布缺少方向
的成功图。面板高度可按需要小幅增加，为正例和负例分别保留独立文字行；不修订本任务之外
的全局轴标签布局。

## 测试与验收

严格按 TDD 执行：

1. 先增加失败测试，解析真实生成的 SVG/HTML，证明三个面板缺少可见正例说明和方向箭头；
2. 测试逐个平台断言 `正例 PASS`、正确成功 reason code、起点/目标图例和非退化箭头；
3. 增加重复末点或不足两个不同点的失败测试，确保 fail closed 且不发布部分目录；
4. 运行可视化 focused tests、完整 source-first 测试、Python 编译和离线发布校验；
5. 用两次正式结果生成新目录，核验输入哈希、五文件集合和跨运行 SVG 字节一致；
6. 使用 Firefox 实际渲染，并确认无需解释即可看到三类正例、三类负例及路线方向。

验收不重新运行 Action，也不以新图片替代原 JSON/JUnit 正式证据。
