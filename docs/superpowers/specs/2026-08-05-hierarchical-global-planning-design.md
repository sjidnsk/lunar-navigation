# 分层全局规划与局部物理认证设计

日期：2026-08-05

状态：已实施；Ubuntu 自动化验证完成

## 1. 背景与问题

当前 `lunar_planner_core` 的轮式、腿式和跳跃式后端都使用
`PlannerInput.world.local_map` 完成实际搜索或认证。`global_map` 虽然进入一致世界快照，
但没有参与全局路线搜索。合成 RViz 实验为了允许用户在完整地图内选点，把相同的整图数据
同时发布为全局图和局部图，结果导致局部高维规划器承担整图搜索：

- 轮式状态包含 `(x, y, yaw, motion_mode)`；
- 腿式状态包含 `(x, y, yaw, reachable_body_z)`；
- 两者在 ARA* 前预先展开可达格点；
- 跳跃式只认证一次跳跃，没有完整多跳拓扑搜索。

这使 `50 m × 50 m、0.2 m` 的 62,500 个二维栅格膨胀为数百万个潜在高维
状态，造成状态上限、长时间搜索和远距离跳跃失败。问题的根因是缺少全局规划层，而不是
RViz、GPU 或地图尺寸本身。

## 2. 已批准决策

1. 正式全局规划层进入主仓 C++ `lunar_planner_core`，不是仓库外演示替身。
2. 每次 `PlanMotion` 返回完整全局路线预览和当前已认证局部执行段。
3. `Planner::Plan(const PlannerInput&)` 保持无状态；局部段完成或环境变化后由外部执行器
   重新提交最终目标。
4. 不修改 `PlanMotion.action` 或 `MotionReference.msg` schema。
5. 路线采用安全优先、确定性的代价与平局规则。
6. 轮式和腿式使用能力相关的二维全局搜索，现有高维格点只负责局部段。
7. 跳跃式使用安全落区拓扑搜索，完整路线仅作预览，只授权下一跳。
8. 全局地图采用确定性多分辨率规则，不按“50 m”或“1 km”等场景名称分支。
9. 三类平台都接受大范围目标，但跳跃式只有在地图分辨率、物理能力和资源上限允许时才
   成功；资源不足与物理无路必须区分。
10. 禁止在新全局层失败后回退旧 Python A*、Nav2 或其他隐藏后端。

## 3. 目标

- 让 `global_map` 真正参与从当前状态到最终目标的全局路线搜索。
- 在完整地图上提供可审阅的轮式、腿式或跳跃式路线预览。
- 只把有限路线前缀交给现有局部规划器，消除整图高维状态爆炸。
- 保留现有平台能力、地形安全投影、连续碰撞检查、轨迹优化和跳跃物理认证。
- 支持从小范围高精度地图到大范围粗粒度地图的统一资源规则。
- 保持 Action schema、取消/替换语义、单快照一致性和 C++ v3 唯一生产内核边界。
- 在 Ubuntu 22.04 amd64 与 Jetson AGX Orin 上分别建立按栅格规模分档的性能门槛。

## 4. 非目标

- 本阶段不新增地图瓦片 Topic 或瓦片缓存；L4 后仍超限时明确拒绝。
- 不让一个 Action 持续执行到最终目标，也不在核心中保存跨请求路线缓存。
- 不一次性生成并认证完整轮式/腿式可执行轨迹。
- 不一次性授权跳跃式全部多跳段。
- 不改变外部地图数据所有权，不由规划核心重新发布同名地图 Topic。
- 不把未经局部认证的全局路线预览当作执行指令。
- 不修改 PPO 网络结构、ROS Action schema 或外部任务消息；受规划行为变化影响的 PPO
  等价性与重训由单独工作项处理。

## 5. 总体架构

`Planner::Plan()` 保留一个公开入口，内部改为四阶段流水线：

```text
一致世界快照
    │
    ▼
GlobalRoutePlanner
    在 global_map/map 中生成完整能力相关路线
    │
    ▼
LocalFrontierSelector
    选择当前 local_map 可覆盖的最远安全航点或下一落区
    │
    ▼
现有 wheel / legged / hopper 局部后端
    生成局部轨迹或认证下一跳
    │
    ▼
ReferenceComposer
    合成 map 全局预览与 odom 当前执行段
```

### 5.1 `GlobalRoutePlanner`

负责：

- 校验全局地图层级与平台分辨率门槛；
- 在全局图上构建平台相关 `SafeProjection`；
- 分派轮式/腿式二维搜索或跳跃式落区拓扑搜索；
- 返回不可变 `GlobalRoute`、总代价、展开状态和稳定原因码。

该组件不调用局部运动格点，不生成可执行轨迹。

### 5.2 `LocalFrontierSelector`

负责：

- 将全局路线从 `map` 变换到 `odom`；
- 与实际 `local_map` 覆盖范围、局部视距和安全走廊求交；
- 选择最远安全局部航点；
- 在局部后端失败时按确定顺序缩短航点；
- 为局部后端建立请求内不可变的有限地图视图。

该组件不修改或重新发布外部地图。

### 5.3 平台局部后端

现有轮式、腿式和跳跃式模块保留其平台职责：

- 轮式：运动原语格点、连续扫掠验证、走廊和样条优化；
- 腿式：身体运动格点、地形/高度可达性、走廊和身体参考优化；
- 跳跃式：保持区、落区、弹道、飞行管和第一跳认证。

局部后端改为消费内部 `LocalPlanningProblem`，其中只包含 `goal_odom`、有限局部视图、
当前状态、能力、配置和停止令牌，不再隐式读取整份 `PlannerInput`。

### 5.4 `ReferenceComposer`

负责把 `GlobalRoute` 和局部后端结果组合为一个 `MotionReference`：

- 全局预览与当前执行数据分开保存；
- 没有已认证局部执行段时禁止创建有效参考；
- 汇总全局/局部诊断，不改变稳定 Outcome/Directive 语义。

## 6. 坐标系与核心输入语义

Action 继续接受 `map` 或 `odom` 目标。`SnapshotBuilder` 在冻结快照时统一生成
`goal_map`：

- 输入为 `map` 时保持目标坐标；
- 输入为 `odom` 时使用冻结的 `map_from_odom` 转换到 `map`；
- 当前平台状态继续保持 `odom`；
- 全局规划前把当前状态从 `odom` 转换到 `map`；
- 局部航点从 `map` 反变换到 `odom` 后交给局部后端。

核心字段从含糊的 `goal` 改为语义明确的 `goal_map`。C++ 编译错误必须迫使内部调用方、
测试 fixture 和 PPO 训练桥显式更新，不能提供同时接受两种隐式 frame 的兼容分支。

ROS 输出使用消息中已有的独立 Header：

- `MotionReference.header.frame_id = map`；
- `path_preview.header.frame_id = map`；
- `trajectory.header.frame_id = odom`；
- 每个已授权 `HopSegment.header.frame_id = odom`。

## 7. 多分辨率全局地图规则

### 7.1 金字塔层级

设任务的最高精度规划分辨率为 `r0`，当前默认 `0.2 m`。`r0` 在 Lifecycle configure
时冻结，并要求 `local_map.resolution = r0`。全局允许层级为：

```text
r_l = r0 × 2^l,  l ∈ {0, 1, 2, 3, 4}
```

默认层级为：

| 层级 | 分辨率 |
|---|---:|
| L0 | 0.2 m |
| L1 | 0.4 m |
| L2 | 0.8 m |
| L3 | 1.6 m |
| L4 | 3.2 m |

设地图物理宽、高为 `Sx`、`Sy`，选择满足下式的最小层级：

```text
ceil(Sx / r_l) × ceil(Sy / r_l) <= 1,048,576

且

max(ceil(Sx / r_l), ceil(Sy / r_l)) <= 4,096
```

始终选择满足资源条件的最精细层级。收到的全局图分辨率不属于金字塔、比应选层级更粗，
或比应选层级更细而违反资源限制时，快照构建失败。L4 仍不能满足条件时返回
`GLOBAL_MAP_SCALE_UNSUPPORTED`；本阶段不得继续静默降低分辨率。

公式适用于任意地图范围。具体物理尺寸只能作为公式示例，不能进入代码分支。

### 7.2 保守聚合

全局地图生产方按照以下规则从四个子单元聚合一个父单元：

| 图层 | 聚合规则 |
|---|---|
| `valid_mask` | 所有子单元有效才为有效 |
| `obstacle` | 任一子单元为真即为真 |
| `forbidden` | 任一子单元为真即为真 |
| `obstacle_height` | 最大值 |
| `observation_age_s` | 最大值 |
| `observation_quality` | 最小值 |
| `observation_count` | 最小值 |
| `obstacle_variance` | 最大值 |
| `elevation` | 所有有效子单元的均值；存在无效子单元时父单元无效 |
| `elevation_variance` | 最大子单元自身方差加子单元高程的总体方差 |

该规则允许粗层保守地关闭窄通道，但禁止通过平均化把已知障碍、陈旧观测或高程突变变成
自由空间。核心能够校验层级、形状和数值，不能仅从单层消息证明聚合来源；发布方的聚合
版本和验证证据属于外部地图接口基线与集成验收。

### 7.3 平台相关分辨率门槛

通用金字塔选择之后仍须应用平台可表达性检查。跳跃式必须先从能力参数、月面重力、允许
飞行时间、起跳速度和着陆速度求出保守最大水平可达距离 `R_hop_max`，并满足：

```text
global_map.resolution <= R_hop_max / 2
```

不满足时返回 `HOPPER_GLOBAL_RESOLUTION_INSUFFICIENT`，表示地图表达资源不足，不得误报为
物理无路。轮式和腿式允许使用较粗全局层，因为全局路线不是执行轨迹；所有真实通过性仍由
L0 局部图认证。

## 8. 轮式与腿式全局搜索

### 8.1 搜索状态与邻接

- 状态仅为全局栅格 `(x, y)`；
- 使用 8 邻域；
- 对角移动只有在目标格和两个相邻正交格都硬可行时才允许，禁止切角；
- 邻居在状态展开时按需生成，不预建完整邻接图；
- 邻居顺序、栅格索引和平局规则固定，保证相同输入产生相同路线。

全局搜索是 C++ v3 的正式组成部分。它可以复用现有 ARA* 的资源、候选排序和确定性策略，
但不得复用要求预生成高维可达图的轮式/腿式格点构建方式。

### 8.2 硬安全约束

每个平台分别在 `global_map` 上调用 `BuildSafeProjection`。候选栅格必须满足：

- 已知且观测年龄、质量、次数有效；
- 非障碍、非禁入；
- 满足项目与平台能力中更严格的坡度限制；
- 满足平台粗糙度、净空和不确定性限制；
- 起点和至少一个目标容差栅格位于同一安全连通分量。

轮式和腿式不得共享一张预计算的通用可通行掩码；相同地图允许产生不同路线或不同结果。

### 8.3 代价与启发函数

边代价由非负项组成：

- 几何步长；
- 按平台保守速度估计的时间；
- 坡度平方风险；
- 粗糙度风险；
- 接近最低允许净空时的连续惩罚。

硬不可行单元永远不能通过提高代价重新进入候选集。所有软权重进入版本化配置并在 configure
时冻结。启发函数只使用到目标区域的直线距离除以平台最大速度，不计风险项，确保不高估。

### 8.4 路线简化与目标朝向

搜索结果先保留原始栅格链，再执行确定性视线简化。只有 supercover 直线经过的每个单元和
每个对角夹角均满足硬安全条件时，才能删除中间点。

- 中间局部航点使用全局路线切线方向和宽松 yaw 容差；
- 腿式允许局部后端根据横移能力调整身体朝向；
- 最终局部段恢复用户指定 yaw 与原始容差；
- 全局层不把二维路线伪装成已认证的轮式或腿式运动学轨迹。

## 9. 跳跃式全局搜索

### 9.1 落区节点

全局安全投影按跳跃能力筛选满足坡度、粗糙度、平面残差、有效面积、侧向净空和顶部净空的
候选落区。当前保持区和目标容差内落区必须显式加入。候选采用稳定栅格顺序，并受
`maximum_graph_nodes` 限制。

粗层落区只提供保守拓扑候选，不构成执行授权。下一跳的起点、落区和完整飞行管必须在 L0
局部图上重新认证。

### 9.2 候选边与图搜索

只有同时满足以下条件的两个落区才建立候选边：

- 水平和高程差位于能力推导的弹道包络内；
- 预计飞行时间、起跳速度、冲量和着陆速度不超限；
- 低成本全局飞行管检查没有发现确定障碍；
- 每个节点只保留按稳定代价排序的 `maximum_graph_out_degree` 条边。

图搜索代价综合跳数、预计飞行时间、稳定等待时间、冲量和落区风险。完整节点链进入全局
预览；现有 `CertifyFirstHop` 只对第一条边执行高精度认证并生成唯一已授权 `HopSegment`。

默认继续使用现有 `maximum_graph_nodes=128`、`maximum_graph_out_degree=8` 和
`maximum_authorized_hops=1`。部署可显式提高图资源，但必须重新通过对应栅格档位的性能和
内存验收。因节点或路线长度上限无法证明完整路径时返回
`HOPPER_GLOBAL_ROUTE_RESOURCE_LIMIT`，与完整搜索确认无路严格区分。

## 10. 局部航点和有限规划视图

`LocalFrontierSelector` 从全局路线起点向前扫描，选择满足以下条件的最远候选：

- 位于有效 `local_map` 内；
- 距局部图边界保留平台外形支撑半径、最小净空和跟踪误差余量；
- 从当前状态到候选的完整路线前缀均有 L0 数据覆盖；
- 候选与当前状态在局部安全投影中连通；
- 跳跃式候选是全局落区链中的下一节点，且完整飞行管位于局部覆盖范围内。

局部规划视图为以下交集：

```text
实际 local_map
  ∩ 平台周围最大局部视距
  ∩ 全局路线前缀安全走廊
```

默认配置：

| 配置 | 默认值 |
|---|---:|
| 轮式局部路线视距 | 4.0 m |
| 腿式局部路线视距 | 3.0 m |
| 局部航点最大尝试数 | 3 |

轮式和腿式安全走廊半宽为：

```text
平台外形支撑半径 + 平台最小净空 + 0.4 m 附加余量
```

局部后端首先尝试最远候选；失败后按路线距离依次缩短，最多三次。全部失败时返回
`LOCAL_SEGMENT_INFEASIBLE`。没有满足覆盖要求的前进候选时返回
`LOCAL_MAP_COVERAGE_INSUFFICIENT`。全局路线存在但局部段不可执行时不得返回参考。

## 11. 输出和 Action 语义

内部 `MotionReference` 增加独立 `GlobalRoutePreview`，ROS 消息 schema 保持不变：

- `path_preview`：完整全局路线或完整落区节点链，frame 为 `map`；
- `trajectory`：轮式/腿式当前已认证局部执行段，frame 为 `odom`；
- `hops`：跳跃式只包含下一次已认证跳跃，frame 为 `odom`。

跳跃式后续名义落区可以出现在 `path_preview`，但不能出现在 `hops`。存在后续未授权路线时
加入 `HOPPER_REMAINING_HOPS_PREVIEW_ONLY`。使用较近局部航点后加入
`LOCAL_FRONTIER_BACKOFF`。

只有以下情况可以返回 `NEW_REFERENCE_AVAILABLE` 或
`SAFE_FRONTIER_REFERENCE_AVAILABLE`：

1. 存在完整全局拓扑路线；
2. 存在当前已认证、可执行的局部轨迹或下一跳；
3. 参考平台类型、frame、时间和地图快照均一致。

仅有全局路线预览时不得构造空 trajectory/hops 的成功参考。

## 12. ROS 快照、地图契约和滚动重规划

### 12.1 Topic 语义

不新增外部 Topic：

- `/environment/map_global`：`map` frame，发布公式选择的全局层级；
- `/environment/map_local`：`odom` frame，发布当前平台附近的 L0 窗口；
- `/localization/odometry`、`/localization/status`、`/tf` 和 mission 输入保持不变。

`SnapshotBuilder` 继续校验缺失、过期和跨消息时间偏差，并新增：

- `r0` 与金字塔层级校验；
- 全局栅格数与单轴限制；
- 平台相关分辨率门槛；
- map/odom 目标规范化；
- 结果上下文中独立 preview frame 与 execution frame。

地图生产方负责按照本设计发布保守聚合层。核心不得在接收到超大消息后静默临时降采样，
也不得用 `global_map` 代替缺失或过期的 `local_map`。

### 12.2 无状态滚动重规划

外部执行器保留最终目标，并在以下事件重新提交 `PlanMotion`：

- 当前局部段完成；
- 新全局或局部地图影响尚未执行路线；
- 平台偏离当前安全走廊；
- `map_from_odom` 发生超限变化；
- 当前执行或局部认证失败；
- 任务取消、暂停或替换目标。

每个请求重新冻结输入并重新规划，不复用隐藏路线缓存。现有 Action cancel、replace、
`ReferenceGuard` 和单 worker 规则保持不变。

## 13. 资源与性能门槛

### 13.1 默认资源

| 配置 | 默认值 |
|---|---:|
| 全局最大栅格数 | 1,048,576 |
| 全局单轴最大栅格数 | 4,096 |
| 全局最大展开状态 | 1,048,576 |
| 全局最大 Open 状态 | 1,048,576 |
| 全局搜索工作内存 | 256 MiB |
| 最大输出路线点 | 4,096 |
| 跳跃全局图节点 | 128 |
| 跳跃全局图出度 | 8 |
| 跳跃授权段数 | 1 |

所有长循环必须检查 `stop_token`。算法使用状态、候选、Open 集合和内存上限保证有界；不使用
会因主机瞬时负载改变搜索结论的内部墙钟超时。

### 13.2 性能分档

| 全局栅格数 | Ubuntu全局搜索p95 | AGX全局搜索p95 | Ubuntu完整Action p95 | AGX完整Action p95 |
|---:|---:|---:|---:|---:|
| ≤65,536 | 0.5 s | 1.0 s | 2.0 s | 3.0 s |
| ≤262,144 | 1.0 s | 2.0 s | 3.0 s | 4.0 s |
| ≤1,048,576 | 2.0 s | 4.0 s | 4.0 s | 6.0 s |

核心基准测量纯规划阶段；完整 Action 从服务器接受目标到结果转换完成，包含快照适配、全局
搜索、局部规划、认证和消息转换，不包含 RViz 渲染延迟。Ubuntu 当前 RTX 4080 SUPER
主机负责开发验收；AGX Orin 指标只有在设备上测量后才能形成正式结论。

## 14. 稳定失败语义

| 情况 | PlanningOutcome | reason_code |
|---|---|---|
| 地图层级不属于金字塔或不是允许的最精细层 | `INVALID_REQUEST` | `GLOBAL_MAP_LEVEL_INVALID` |
| L4 仍超过全局规模限制 | `RESOURCE_EXHAUSTED` | `GLOBAL_MAP_SCALE_UNSUPPORTED` |
| 全局目标没有安全容差单元 | `GOAL_INFEASIBLE` | `GLOBAL_GOAL_INFEASIBLE` |
| 完整搜索确认不存在安全路线 | `NO_KNOWN_SAFE_ROUTE` | `GLOBAL_NO_KNOWN_SAFE_ROUTE` |
| 全局状态、Open 或内存耗尽 | `RESOURCE_EXHAUSTED` | `GLOBAL_SEARCH_RESOURCE_LIMIT` |
| 跳跃全局层级不能表达单跳能力 | `RESOURCE_EXHAUSTED` | `HOPPER_GLOBAL_RESOLUTION_INSUFFICIENT` |
| 跳跃图资源不足以证明完整路线 | `RESOURCE_EXHAUSTED` | `HOPPER_GLOBAL_ROUTE_RESOURCE_LIMIT` |
| 局部图无法覆盖安全前进航点 | `NO_KNOWN_SAFE_ROUTE` | `LOCAL_MAP_COVERAGE_INSUFFICIENT` |
| 三次局部航点尝试均失败 | `NO_KNOWN_SAFE_ROUTE` | `LOCAL_SEGMENT_INFEASIBLE` |
| 第一跳高精度认证失败 | `NO_KNOWN_SAFE_ROUTE` | 保留具体弹道或飞行管稳定原因码 |
| 请求取消 | `CANCELED` | `REQUEST_CANCELED` |
| 内部不变量破坏 | `NUMERICAL_FAILURE` | 对应稳定内部原因码 |

输入缺失、过期、TF 外推、定位不可用和 mission 状态继续使用现有 Snapshot/Action 错误映射。
资源限制不得伪装成 `NO_KNOWN_SAFE_ROUTE`，未经完整搜索的结果也不得声称物理不可达。

## 15. 诊断

现有 `PlannerDiagnostics.msg` 不变：

- `planner_name = cpp_v3_hierarchical`；
- `elapsed_s` 为完整核心调用耗时；
- `expanded_states` 为全局和局部展开状态之和；
- `best_cost` 为完整全局路线代价；
- `warning_codes` 保存局部航点回退和未授权跳跃预览等稳定警告。

标准 `/diagnostics` 增加键值：

- 金字塔层级、全局分辨率、全局栅格数；
- 全局和局部各自耗时、展开状态、Open 峰值和估算工作内存；
- 全局路线长度、简化前后点数；
- 局部航点距离、尝试次数和走廊宽度；
- 跳跃图节点、边、路线跳数和第一跳认证次数。

## 16. RViz 行为

RViz 继续只显示当前选择平台，并增加分层表达：

- 全局地图显示当前 `Lx`、分辨率、栅格数和完整范围；
- 轮式全局路线为浅蓝，当前执行段为高亮粗蓝；
- 腿式全局路线为浅绿，当前执行段为高亮粗绿；
- 跳跃式后续名义落区和连线为浅橙，已认证下一跳显示实线弹道、飞行管和落区；
- 局部航点使用独立标记；
- 不可行目标保留红色目标和稳定原因，不绘制虚假路线。

左侧面板增加 map level、全局分辨率、栅格数、路线长度、局部航点距离、全局/局部耗时和
跳数。Action 消息只提供数据，仓库外 RViz 控制器负责颜色、线宽和 Marker 表达。

合成 RViz 桥必须改为：

- 目标合法性根据全局图判断；
- `local_map` 只发布当前平台附近的 L0 窗口；
- 不再把完整全局图复制为每个平台局部图；
- 当前确定性随机地图仍不强制连通，也不为得到规划正例而重采样。

## 17. 测试与验收

### 17.1 单元测试

- 金字塔层级：边界尺寸、狭长地图、L0–L4 切换、非层级分辨率和超限拒绝；
- 保守聚合：固定小矩阵逐单元验证 AND、OR、最大、最小、均值和总方差；
- 全局搜索：禁止切角、平台差异、目标容差、确定性平局、取消和资源耗尽；
- 路线简化：任何简化线段的 supercover 单元均通过硬安全验证；
- 坐标变换：map 全局目标、odom 状态、局部航点和非单位 TF；
- 局部选择：边界余量、有限视图、最远航点和三次确定性回退；
- 跳跃图：多跳正例、分辨率不足、资源截断、真正无路和只授权第一跳；
- 消息转换：preview 与 execution 使用不同 frame 且 schema 不变。

### 17.2 自动化集成测试

使用固定字面起终点，不在测试运行期间扫描地图寻找可行目标：

- 远距离轮式正例和障碍隔断反例；
- 远距离腿式正例，以及轮式不可过、腿式可过的平台差异例；
- 跳跃式多跳正例、落区中断反例、分辨率不足和资源不足反例；
- 全局路线成功但首个局部段失败时无参考；
- 地图更新、定位变换、Action cancel/replace 和任务暂停；
- RViz 全局预览、当前局部高亮、跳跃预览/授权区分和红色失败目标；
- 原 Isaac 六案例和合成 RViz 启动入口继续回归。

随机交互地图保持“不检查连通性”的批准语义。规划正反例使用独立确定性 fixture，不能修改
随机生成器使结果迎合规划器。

### 17.3 性能与确定性

每个栅格规模档位至少覆盖空旷图、固定随机障碍图、窄通道图和无路最坏情况。每个 fixture
预热后运行至少 30 次，记录 p50、p95、最大值、展开状态、Open 峰值和峰值内存。

相同输入重复运行时，以下内容必须完全一致：

- PlanningOutcome、ExecutionDirective 和 reason code；
- 全局路线点、局部航点和参考类型；
- 路线代价、路线哈希和警告码顺序。

### 17.4 验收条件

1. `global_map` 实际参与三平台全局决策。
2. 轮式/腿式不再把整张全局图展开为高维格点。
3. 成功结果同时包含完整 `map` 路线和当前 `odom` 执行段。
4. 跳跃成功结果包含完整名义落区链，但只授权第一跳。
5. 资源不足、地图表达不足、物理无路和局部执行失败可明确区分。
6. 三个性能档位满足对应主机门槛，且无不受控内存增长。
7. 现有 Action 并发、取消、替换、快照和六案例回归保持通过。
8. 生产安装包中不存在旧 Python A*、Nav2 fallback 或新的隐藏规划后端。

## 18. 兼容性与后续影响

- ROS Action 和 MotionReference schema 不变，但 `path_preview` 从“局部轨迹副本”升级为
  “完整全局路线”；所有消费者必须按 Header 而不是假设统一 odom frame。
- C++ `PlannerInput` 的目标字段和局部后端内部接口会发生源码级变化，必须原子更新核心、ROS
  适配、测试和训练桥。
- 规划器名称改为 `cpp_v3_hierarchical`，旧局部-only 结果不得与新结果混合统计。
- 旧 v3 规划行为生成的 PPO 数据、checkpoint 或黄金结果不能自动声明兼容；需单独做等价性
  评估，并在不等价时重新训练和重新发布模型包。
- 外部地图接口类型不变，但多分辨率与保守聚合语义需要写入
  `docs/interfaces/external-input-baseline.md` 和对应配置检查；真正上游接管时仍遵守原子切换规则。
- AGX 性能指标必须在设备上测量；Ubuntu 只能证明开发与仿真门槛。
