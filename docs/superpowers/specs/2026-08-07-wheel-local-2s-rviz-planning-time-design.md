# 轮式局部规划 2 秒指标与 RViz 规划耗时设计

日期：2026-08-07

状态：已按用户给定的 2 秒指标和后续直接执行授权冻结

## 1. 问题与实测基线

当前 Ubuntu 22.04 amd64 主机为 Intel Core i7-14700KF、RTX 4080 SUPER、ROS 2 Humble；
28 个逻辑 CPU 均处于 `powersave` governor。主仓为 `integration@c475658`，外部 RViz
验证仓为 `main@0861e54`，当前组合构建为 Release。

在固定合成地图 `synthetic-ad1d8d34d49c1056` 上，从轮式起点
`(-18.0, -16.0)` 规划到 `(18.0, -14.8)` 的隔离复现得到：

| 请求 | 全局耗时 | 当前报告的局部耗时 | 局部候选尝试 | 局部展开状态 | 用户等待时间 |
|---|---:|---:|---:|---:|---:|
| 首次请求 | 约 0.10 s | 约 6.37 s | 4 | 50,936 | 约 49.5 s |
| 路线复用后的滚动请求 | 0 s | 约 11.02 s | 7 | 87,488 | 约 11.3 s |

滚动请求没有重复全局 A*；10 秒主要来自同一起点、同一局部地图走廊上的多个前沿候选
被逐个交给轮式格点规划器，每个候选都重新构建安全投影并执行一棵完整 A*。首请求还会在
条件走廊失败后重做全局路线，而现有诊断只保留最后一轮全局和局部耗时，所以各阶段数字
不能解释用户实际等待时间。

RViz 面板目前已有 `Global / local time` 和 `Search / local time` 两行，但两者显示的是
同一组最终轮次数据；没有清晰的规划总耗时、跨重试累计局部耗时、2 秒指标或超标状态。

## 2. 目标与验收口径

1. 在上述固定合成地图和当前轮式 v2 能力上，Release 构建的滚动轮式局部规划
   `p95 <= 2.000 s`。
2. 每个 RViz 请求都显示其实际局部累计耗时；单次值 `<= 2.000 s` 显示 `PASS`，否则显示
   `FAIL`。不通过改写、截断或隐藏耗时来满足指标。
3. `PlannerDiagnostics.elapsed` 继续表示一次核心 `Planner::Plan()` 的完整耗时；分层诊断
   改为报告跨全部条件走廊重试的累计全局和累计局部耗时。
4. 不增加 2 秒墙钟超时，不恢复固定展开数、开放列表或候选数上限。有限局部地图和取消
   `stop_token` 仍是自然搜索边界；2 秒只作为 Release 性能回归门槛。
5. 不降低轮式外形、0.20 m 障碍净空、扫掠碰撞验证、坡度/越障限制或确定性要求。
6. 不修改 ROS Action 或消息 schema。

其中 `p95` 使用 1 次预热加至少 20 次测量；测试报告同时保存 `p50`、`p95`、最大值、
逻辑前沿数、实际格点遍历数和展开状态。RViz 的 `PASS/FAIL` 始终按当前这一次请求判断，
不是按统计分位数判断。

## 3. 方案比较

### 方案 A：只替换容器和缓存投影

把 `std::map/std::set` 换成直接索引状态表和二叉堆，并缓存安全投影。风险较低，但当前滚动
请求执行 7 棵搜索；即使单棵搜索加速两到三倍，也不能可靠保证累计 2 秒。

### 方案 B：共享一次完整搜索并优化热路径（采用）

以最远前沿对应的走廊视图为公共局部搜索域。轮式格点首先搜索最远前沿；若开放列表耗尽
仍不可达，不丢弃已经完整探索的节点、最短代价和父链，而是在同一棵搜索树上按从远到近
检查其余前沿的精确终端连接，选择最远的可达前沿。随后把状态索引改为固定维度直接索引，
Open 改为带稳定序号的二叉堆和惰性失效检查。

这样逻辑上仍检查全部前沿、仍能在有限地图耗尽后证明不可达，但每个全局路线轮次只进行
一次格点遍历。最远走廊是所有较近前沿走廊的超集，所有返回边仍通过相同的
`SafeProjection` 和连续扫掠验证，因此不会降低安全性。

### 方案 C：2 秒到时返回当前最好路线

实现简单，但会把“尚未搜索完成”混为“可行”或“不可行”，并违反已批准的完整搜索语义，
不采用。

## 4. 主仓算法设计

### 4.1 排序前沿合同

`BuildLocalFrontiers()` 继续生成从远到近的确定性前沿及距离。轮式调用不再逐个调用
`WheelPlanner::Plan()`，而是把：

- 最远候选的公共 `LocalPlanningProblem`；
- 全部按距离降序排列的 `GoalRegion`；

交给新的轮式 ranked-frontier 入口。足式现有流程本轮不改变。

若最远候选就是最终任务目标，仍保留原目标位置和偏航容差。较近候选继续使用路线切向
偏航和既有容差规则。

### 4.2 单棵轮式格点树

`SearchWheelLattice()` 增加 ranked-goal 结果：

- 以最远目标的可采纳启发式执行现有 A*；
- 最远目标找到时保持现有最优终止条件；
- 最远目标不可达时，只有 Open 真正耗尽后才扫描已探索节点；
- 对其余目标按从远到近执行位置、偏航、曲率和扫掠终端连接检查；
- 对第一个存在连接的目标选取总代价最低的父节点和终端边；
- 返回选中的前沿索引、唯一格点遍历次数、展开状态和原有离散路径。

取消、无有效起步边、输入非法和内存分配失败维持原有稳定原因码，不进入前沿回退扫描。

### 4.3 热路径容器

轮式状态天然由 `(cell_x, cell_y, yaw_bin, motion_mode)` 构成。使用局部地图宽高、偏航桶数
和三个运动模式计算无碰撞的线性索引：

```text
index = (((y * width + x) * yaw_bins + yaw_bin) * 3 + motion_mode)
```

状态表改为固定长度索引数组，未发现状态使用哨兵值。Open 使用 `std::priority_queue`；更新
节点时压入新条目，弹出时通过节点当前代价和稳定序号丢弃旧条目。比较键继续包含
`f、g、state、sequence、node_index`，保证相同输入产生相同输出。

### 4.4 条件走廊重试

ranked 搜索选中较近前沿时继续触发现有 `GLOBAL_CONDITIONAL_CORRIDOR_RETRY` 语义；全局
改线后再进行一棵新的局部树。诊断必须累计此前已花费的全局和局部时间、展开状态和遍历数，
不能只显示最后一轮。

## 5. 诊断与 RViz 设计

不修改消息定义。主仓通过既有 `/diagnostics` KeyValue 合同新增或明确以下值：

| 字段 | 含义 |
|---|---|
| `planner_total_elapsed_s` | 本次核心 `Planner::Plan()` 完整耗时 |
| `global_search_elapsed_s` | 所有全局路线尝试累计耗时 |
| `local_planning_elapsed_s` | 所有轮式局部树累计耗时 |
| `hierarchical_local_attempts` | 逻辑上检查到选中前沿为止的候选数 |
| `hierarchical_local_search_runs` | 实际执行的格点树数量 |
| `hierarchical_global_replans` | 条件走廊造成的全局重算次数 |

外部控制器只转发属于当前 request generation 且 reason code 匹配的终态诊断。RViz 左侧面板
把现有含糊的重复行整理为：

```text
Planner total          1.842 s
Global cumulative      0.102 s
Wheel local cumulative 1.706 / 2.000 s  PASS
Frontiers / searches   7 / 1
Global replans         0
```

规划中继续显示 Action phase；收到 Action feedback 时显示当前 `elapsed_s`。终态以
`result.diagnostics.elapsed_s` 和同 request 的主仓诊断覆盖临时值。轮式局部超过 2 秒时使用
红色粗体 `FAIL`，达标为绿色 `PASS`；非轮式平台显示实际耗时但不套用轮式 2 秒判定。

非法、缺失、负数、非有限或跨 request 的耗时必须 fail closed 为 `unknown`，不得沿用上次
结果。

## 6. 测试与证据

### 主仓

- ranked 轮式搜索：最远可达、最远不可达但较近可达、全部不可达、偏航不符、取消和确定性；
- 容器替换前后的既有单目标引用哈希和稳定平局行为；
- 分层规划只执行一棵轮式树但保留逻辑前沿回退警告；
- 条件走廊重算时累计耗时、展开状态、局部树数和全局重算数；
- 新增含障碍和前沿回退的 Release 压力 case，1 次预热、20 次测量，轮式局部 p95 不超过
  2.000 秒；既有三平台资格 case 继续通过。

### 外部 RViz 仓

- Python 诊断桥测试覆盖总耗时、累计耗时、请求隔离和非法值；
- Qt Panel 测试覆盖轮式 PASS、轮式 FAIL、非轮式无预算判定和终态清空；
- 使用 seed `20260805`、50 m、0.2 m、12% 障碍图执行真实进程回归；验证首次请求、路线
  复用后的滚动请求、局部累计耗时和面板诊断字段；
- 组合构建必须为 Release，使用新的独立 install，不覆盖正在运行的 RViz install。

性能结果写入 `~/CodexDownloads/lunar_navigation/wheel-local-2s-rviz-timing/evidence`，不提交
运行 artifact。旧 Isaac 冻结快照仍只作为历史证据，不重新定基线。

## 7. 仓库和合入边界

- 主仓改动位于 `feature/wheel-local-2s-rviz-timing`，通过资格检查后快进合入 `integration`。
