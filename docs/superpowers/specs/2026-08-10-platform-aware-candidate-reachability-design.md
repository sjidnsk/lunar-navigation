# 平台化候选可达性快速修复设计

**日期：** 2026-08-10
**状态：** 已批准，待实施
**范围：** 正式 PPO 训练环境的候选预过滤、最小诊断与 checkpoint 兼容恢复

## 1. 目标

保留机器人当时已经掌握的 `0.2 m` 精细观测地图来计算候选预计信息增益，同时修正候选进入策略前的可达性语义：轮式、腿式和飞跃式使用各自的轻量预过滤，最终安全性仍由现有 C++ v3 平台规划器认证。

修复必须满足：

- 不改变 PPO 网络、动作合同、奖励、课程、worker 数量或训练预算；
- 不使用隐藏真值替代机器人当时的观测证据；
- 不为每个候选重复实现或调用完整规划器；
- 不从头训练，允许从修复前 checkpoint 精确恢复；
- 补丁验证完成前不停止当前训练。

## 2. 已确认问题

`CandidateBuilderV2` 当前对所有平台统一执行两项检查：候选终点的 `traversable_ratio` 非零，以及机器人到候选终点的二维栅格直线全部已观测且无障碍。终点投影已经按平台生成，但直线检查不是平台能力模型。

这会产生两类错误：

- 轮式或腿式存在已知绕行路线时，仍可能因直线被挡而提前删除候选；
- Hopper 可以越过地面障碍时，候选可能在进入弹道规划器之前被提前删除。

选中的候选随后已经交给带平台 capability 的 C++ v3 规划器。因此缺口位于“候选预过滤”，不是最终规划器。被预过滤删除的候选不会进入规划 outcome 统计，现有汇总指标只能支持该问题是早停原因之一，不能量化其占比。

## 3. 选定设计

### 3.1 共享候选发现和增益

以下逻辑保持不变：

- 从已观测区域与未知任务 ROI 的边界发现 frontier；
- 排除机器人当前格和已经访问过的落点；
- 保持传感器范围、稳定排序、64 个候选上限和确定性选择；
- 使用当前 `0.2 m` 精细观测状态批量计算预计信息增益；
- 零增益候选不进入策略。

预计信息增益描述“到达后可能看到多少新区域”，不承担平台运动可达性的职责。

### 3.2 分平台轻量预过滤

`CandidateBuilderV2.build(...)` 显式接收 `platform_type`，只接受 `WHEELED`、`LEGGED`、`HOPPER`。

所有平台首先要求候选终点：

- 已被机器人观测；
- 位于任务 ROI；
- 对应平台的 `traversable_ratio` 非零；
- 不是已访问或当前所在格。

对于 `WHEELED` 和 `LEGGED`：

- 在 `observed_mask`、无物理障碍和该平台 `traversable_ratio > 0` 的交集上，从机器人格执行一次确定性的四邻域连通搜索；
- 候选终点属于该连通域才保留；
- 每次 observation 只计算一次连通域，不对每个候选重复搜索；
- 该检查允许已知区域内绕行，但不代替 C++ 规划器的朝向、运动原语、机身扫掠和动力学认证。

对于 `HOPPER`：

- 不执行地面直线或地面连通检查；
- 现有 Hopper 平台投影只作为已观测落点的廉价硬可行预检；
- 单跳能力包络、完整支撑区域、抛物线、飞行管、禁区和数值确定性继续由 C++ v3 Hopper 规划器最终认证；
- 不因预过滤放宽而把候选宣称为安全或可执行。

### 3.3 规划失败与候选耗尽

现有行为保持：规划器拒绝某个已选候选时，只屏蔽该候选；只在活动候选全部耗尽后结束 episode。不得把一个候选的 `GOAL_INFEASIBLE` 或 `NO_KNOWN_SAFE_ROUTE` 提升为整幅地图不可探索。

### 3.4 checkpoint 兼容恢复

候选 mask 的变化会改变活动 observation digest。为避免从头训练，恢复过程采用与现有增益修复相同的单边界迁移：

1. 首先用新平台过滤重建 checkpoint observation；完全匹配则直接恢复。
2. 仅在 observation digest 或已拒候选索引出现已知兼容错误时，用旧通用直线规则重建并验证 checkpoint 中的精确旧边界。
3. 旧边界验证成功后立即开启新平台过滤；从下一次 observation 开始只使用新语义。
4. 其他身份、场景、能力、状态或时间错误继续 fail closed，不得被兼容分支吞掉。

该迁移不修改 PPO 参数，不丢弃已持久化更新，也不需要新增 checkpoint 必填字段。

### 3.5 最小诊断

在不改变策略输入和奖励的前提下，按平台汇总以下计数：

- frontier 锚点数；
- 平台预过滤拒绝数；
- 输出候选数；
- `GOAL_INFEASIBLE`、`NO_KNOWN_SAFE_ROUTE` 等规划 outcome；
- 因候选为空或全部候选被拒而结束的 episode 数。

诊断字段只用于判断问题发生在候选生成、平台预过滤还是最终规划器，不参与 loss 或 checkpoint observation digest。

## 4. 错误处理与确定性

- 未知平台、shape 错误、非有限投影或 observation/canvas 不一致继续 fail closed。
- 连通搜索使用固定邻居顺序，候选排序与 64 项选择规则保持确定性。
- Hopper 最终规划失败继续使用规划器的正式 reason code，不在 Python 猜测失败原因。
- 如果新过滤产生零候选，必须在诊断中记录“生成后为空”而不是伪装成规划器无路。

## 5. 验证

最小回归测试覆盖：

1. 地面直线被障碍阻断但存在已观测绕行路线时，轮式和腿式候选仍保留。
2. 地面直线被障碍阻断时，Hopper 候选不会因地面规则被删除。
3. 未观测、平台投影不可行或已访问的 Hopper 落点仍被拒绝。
4. Hopper 候选进入 C++ 规划器后，飞行管或落区不安全仍被正式拒绝。
5. 修复前 checkpoint 可以先恢复旧 observation 边界，并在下一 observation 切换到新过滤。
6. 相同输入重复构建得到逐位一致的候选 features 和 mask。

运行候选构建、正式 builder、恢复和训练 smoke 的定向测试；随后运行训练包测试集。采样 collect wall time 的下降不得超过现有正式门限 `10%`。

## 6. 切换训练

代码和测试通过前保持当前服务运行。通过后：

1. 对服务执行优雅停止，让主进程保存稳定 checkpoint；
2. 核对 checkpoint step、metrics journal、manifest 和源码提交一致；
3. 从该 checkpoint 创建不可变恢复副本；
4. 使用修复提交恢复，不从 step 0 开始；
5. 连续观察至少 5 个 joint update，分别比较三平台候选耗尽、规划拒绝、覆盖率和回报。

若系统或 PPO 数值健康而某平台仍持续候选耗尽，则依据新增分层计数定位后续修复；本次不顺带修改奖励、课程或规划器能力模型。
